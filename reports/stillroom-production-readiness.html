Stillroom — Production Readiness Audit

NOT READY — Critical security, functional, or deployment problems remain unresolved.
The public deployment serves an older demo without the current social APIs or Clerk login. One high-severity dependency advisory remains. Authenticated cross-account and destructive lifecycle checks were not authorized or executed in this pass.

No publishing, production database changes, schema migrations, test-account creation, real-content deletion, storage writes, or redesign were performed. This report distinguishes executed checks from source inspection and blocked tests.

A. Implemented fixes

  • Malformed request handling: reproduced malformed JSON returning HTTP 500 in development. It now returns a safe HTTP 400. Oversized requests return 413; unsupported compressed requests return 415. Expected parser errors no longer enter the unhandled-error logger, which could include submitted input.
  • Dependency remediation: compatible updates to Clerk JS and Orval, plus supported patched transitive versions of body-parser, qs, undici, fast-uri and Zod 4. Express was already at its latest release; compatible overrides patch its parsers. Initial findings: 7 high, 7 moderate, 2 low. Final findings: 1 high, no moderate, low or critical findings.
  • Regression coverage: added parser-error tests and a reproducible anonymous HTTP smoke script. The script creates no fixtures; optional malformed/unauthorized rejection probes are restricted to development URLs.

Application layouts, pink palette, logo, typography, roles, data schema and product features remain unchanged.

B. Security findings

  • HIGH — unresolved: Zod 3.25.76 is flagged by GHSA-mrhx-c7xc-m3w5 for resource exhaustion during array validation. The scanner recommends 4.6.6 or later. No patched Zod 3 release was found. A major-version migration was not silently applied. The existing 100 KB request cap limits input size but is not proof the vulnerability is fixed.
  • Executed: anonymous profile creation, upload initiation/completion, post deletion, account deletion, Settings access and Board curation requests were denied. A cross-site mutation was rejected with 403.
  • Source inspection: Clerk subjects, not caller-supplied IDs, determine identity. Stored roles gate Fan publishing and Artist curation. Ownership predicates protect edits, comments, reposts and Shelves. Public Shelf reads include a visibility/owner filter. Deletion requires recent first-factor verification and separate Artist-cascade consent; a durable tombstone prevents a deleted session recreating a profile.
  • Not established by source inspection: correct behavior under real authenticated cross-account attacks, email-verification policy, password changes, completed recovery, provider cleanup and session refresh. These remain blocked.
  • Final SAST scan completed with zero findings. Final privacy/dataflow scan returned zero findings. Scanner results are not a substitute for live authorization tests.

C. Database and media findings

  • Development: PostgreSQL queries succeeded. All 16 Stillroom tables were present. Inspected foreign-key constraints were validated; cascades and composite same-Board curation relationships were present. Unique indexes protect normalized usernames, one Board per owner, reposts and saved memberships. Feed, Board, comment, Shelf and discovery-search indexes were present.
  • Read-only consistency checks found zero duplicate/invalid normalized usernames, zero Boards owned by non-Artists, zero original posts authored by non-Fans and zero active profiles matching deletion tombstones. This is a snapshot of existing data, not a migration or concurrency test.
  • Two legacy optional profile-image references (profile image and Board portrait) are UUID fields without database foreign keys. Server ownership/ready-state validation and read filtering protect current paths. Additional database constraints would require a separately reviewed, non-destructive schema change.
  • Production: the production SQL callback reported “This project has no production database.” Required secret names exist, but that does not prove a production database is provisioned, connected or migrated. Production tables, indexes and migration parity remain BLOCKED. No reset, overwrite, push or destructive migration was attempted.
  • Media source inspection: uploads use private persistent App Storage; size/type and signature checks run server-side. Finalization uses the verified object generation and an immutable copy. Public references versus owner-only unattached assets are checked before streaming; video byte ranges are supported. Missing media returned a safe 404.
  • Media retention finding: ordinary post deletion removes the post but does not enqueue reference-aware cleanup of its newly unreferenced stored asset. Account-deletion cleanup is separate and durable. Do not blindly delete assets: other posts, drafts or profile fields may still reference them. A safe cleanup fix and isolated lifecycle tests remain necessary.
  • No ready media assets were available in development. Real photo/video upload, playback, cross-browser delivery, byte ranges and storage erasure were NOT VERIFIED. No files were uploaded for this audit.
  • Deletion jobs retry through a timer and incoming requests. Eventual cleanup while an autoscaled deployment is asleep needs an operational guarantee; no scheduler or infrastructure change was introduced.

G. Remaining reliability and performance issues

  • The stale public release, missing production database verification and Zod 3 advisory block launch certification.
  • Reference-aware ordinary content-media cleanup and reliable execution of delayed deletion jobs require follow-up.
  • Other already-open preview traffic repeatedly requested Board curation and received 404. A fresh browser visit and direct request for the existing Board succeeded. Query strings are intentionally omitted from logs, so the stale/failing request context has not been established; no speculative fix was applied.
  • Feed and Explore are paginated and indexed; comments and Shelf responses are bounded. These facts do not prove scale. No load test was run. Observed smoke timings were roughly 5–33 ms for most requests after the initial health request, not a production benchmark.
  • The frontend build retains an approximately 1.79 MB JavaScript chunk (646 KB gzip), a mobile-performance concern. No architecture or loading strategy was changed. A sampled Explore navigation issued one bootstrap request; duplicate traffic across all routes/sessions was not comprehensively profiled.
