I. Remaining risks and safe next steps

  1. Review Publishing's database settings before approving provisioning. Confirm whether a separate existing production database must be reattached; do not create a replacement if one already exists elsewhere.
  2. If no production database exists, decide whether to provision an empty, schema-only production database. This would not bring development accounts or posts into production. Development-data copying requires separate explicit approval. Do not erase development data as a workaround to obtain an empty production database.
  3. Keep any “overwrite/replace production data” option disabled. Review the exact schema diff and rename/destructive-change warnings before allowing Publish to apply anything. Never run a custom production migration or startup-time schema push.
  4. After approval of the database/hosting path, create a non-promoting preview if the Publishing UI supports it. Keep the current public revision serving while preview checks run.
  5. In that preview, require bootstrap JSON HTTP 200, DB-backed reads, correct current UI/static/media delivery and accessible Clerk flows. Verify production domain/redirect configuration without exposing credentials.
  6. Have an existing authorized account holder verify production sessions and account-specific workflows without creating or deleting real users for testing. Mark anything unavailable as NOT VERIFIED.
  7. If migration validation stalls again, capture that attempt's timestamp, build/preview identifier and migration-validation logs. Do not reset data. Use the Publishing logs and Replit support with the specific attempt evidence if the stall is infrastructure-side.
